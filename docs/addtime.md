## C. 지원 시간

아래 시간은 한국 시간이며, OFF에서는 기존 동작만 사용한다. ON이어도 휴장·적격·실시간 상태 확인에 실패하면 주문하지 않는다.

| 시장 | 공식 시간 | 구현의 신규 자동주문 범위 | 경로 |
|---|---|---|---|
| NXT PRE | 08:00~08:50 | 08:00 이상, 08:50 미만 | NXT, 지정가 `00` |
| KRX regular | 09:00~15:30 | 기존 설정 그대로. 현재 09:02~15:28 | KRX, 지정가 `00` |
| NXT main | 09:00:30~15:20 | 별도 NXT 주문 없음. 정규장은 기존 KRX 경로 유지 | KRX 단일 경로 |
| NXT AFTER | 접수 15:30~, 체결 15:40~20:00 | 15:40 이상, 20:00 미만 | NXT, 지정가 `00` |
| KRX AFTER | 16:00~20:00 | 16:00 이상, 20:00 미만 | KRX, 애프터 지정가 `41` |

08:50~09:00 및 15:30~15:40에는 신규 자동주문이 없다. 15:30 접수 구간에는 실제 연속체결 가격이 없어 선주문하지 않는다. 정규장 전후 차단 시간도 없애지 않았다. 20:00 이후에도 기존 체결 대사·미체결 관리 루프는 수행한다.

주말, KIS 휴장일 조회, 호가 시장상태, 호가시각, 거래정지 상태를 함께 사용한다. 휴장일 조회는 프로세스 내 하루 한 번 캐시하며 조회 실패도 당일 거래 불가로 캐시한다. 재시작하면 다시 조회한다.

`calendar_overrides`는 공지된 특별일을 닫거나 시작을 늦추는 용도다. 새 시간대를 임의로 넓히지 않는다. 연초 특별 개장 공지를 자동 수집하는 기능은 없다. 새 공지는 설정에 반영해야 하며, 미반영 시에도 정상 시장상태·당일 시세 확인 없이는 주문하지 않는다.

## D. 거래소 선택

정규장은 기존 KRX를 유지한다. 프리는 NXT만 사용한다. 15:40~16:00은 NXT, 16:00 이후는 NXT를 우선 확인하고 적격/상태 조건을 충족하지 못하면 KRX AFTER를 확인한다. 같은 신호를 양쪽에 배분하지 않는다.

SOR는 공식 주문 API에 존재하지만, KRX AFTER 전용 `41` 주문의 SOR 조합을 확인하지 못했으므로 사용하지 않았다. 직접 경로 선택은 최선 가격 비교/SOR 구현이 아니며, NXT 우선 정책이 가장 좋은 체결가격을 보장하지 않는다.

NXT는 `cptt_trad_tr_psbl_yn=Y`, `nxt_tr_stop_yn=N`을 요구한다. KRX AFTER는 우선 보통주 `stck_kind_cd=101`, `scty_grp_id_cd=ST`가 확인된 경우만 지원한다. 공식 제도가 허용하는 다른 증권까지 모두 지원한다고 주장하지 않는다. 관리·경고·주의·이상급등·저유동성 등 확인 필드가 없거나 제외 조건에 해당하면 차단한다. 증권사의 추가 거절도 같은 프로세스의 해당 종목/세션/당일 재시도를 막는다.

## E. 가격 출처와 확인 결과

정규장 입력은 원래 `client.quote()`의 KRX 현재가다. 확장 시간은 주문 거래소와 같은 시장구분 `NX`(NXT), `J`(KRX)를 사용한다.

확장 시세는 `inquire-time-itemchartprice`의 `output1.stck_prpr`를 사용한다. 같은 응답의 날짜 있는 분봉 중 현재 세션에 속하고 거래량이 양수인 최근 봉이 있어야 한다. 호가의 `new_mkop_cls_code=20`과 `aspr_acpt_hour`, 현재가 조회의 거래정지 상태도 확인한다. 현재 기본 유효시간은 90초이며 허용 설정은 1~120초다. 분봉으로 신선도를 확인하므로 틱 단위 체결시각 검증과 동일하지 않다. 저유동성 종목은 주문 기회를 놓칠 수 있다.

2026-10-02 08:38:43~45에 005930/NX로 실제 **조회만** 수행했다. 휴장 조회 정상 개장, NXT 적격 Y/정지 N, 호가시장상태 `20`, 호가시각 08:38:44, 당일 08:38 분봉 및 현재가 275,500원을 확인했다. 이 관측은 NXT PRE의 필드 동작을 확인한 것이며, 애프터나 계좌 주문 검증 결과가 아니다.

애프터에서 구형 `40`(시간외 단일가) 또는 `30`(장 종료)를 연속매매 상태로 추측해 허용하지 않았다. 실제 애프터 응답이 `20`이 아니라면 현재 코드는 주문을 차단하며, 공식 정의와 실제 응답을 확인한 뒤 허용 상태를 수정해야 한다. WebSocket은 추가하지 않았다.


## F. 중복 주문과 주문 생애주기

기존 BUY/SELL·LOT·cash·cooldown 가드를 그대로 사용한다. 추가로 세션 주문은 실제 전송 전에 원장에 `INTENT-*` 예약을 하나 기록한다. SQLite `BEGIN IMMEDIATE` 안에서 같은 종목 BUY 또는 같은 LOT SELL의 기존 미결 주문을 검사한다. 응답을 받으면 예약을 실제 주문번호로 원자적으로 바꿔, 예약금과 주문 수를 두 번 더하지 않는다.

세션이 바뀌어도 원주문 세션·거래소·주문구분을 DB에서 복원한다. LOT/WAIT_REENTRY/cooldown을 초기화하지 않는다. 신규 주문의 라우팅과 기존 주문의 취소 경로는 별개다. 취소는 원주문의 거래소, 조회된 원주문 조직번호, 취소 가능 잔량과 주문구분으로 요청한다. 정규장 주문을 애프터 `41`로 바꾸거나 다른 거래소에 재전송하지 않는다.

주문/취소 POST의 통신 결과가 불명확하면 HTTP 수준 자동 재전송을 하지 않는다. 접수 여부를 모르는 `INTENT`는 재시작 후에도 예약을 유지하고 자동 재주문하지 않는다. 취소 가능 목록에서 사라졌다는 이유만으로 취소 완료로 보지 않는다. 원주문 일자·거래소·종목·방향·최종 잔량/취소/체결 수량을 확인한다. 확인 불가 또는 취소 재시도 한도 도달 시 예약을 유지하고 수동 대사가 필요하다는 로그를 남긴다.

체결 조회는 확장 기능 또는 기존 세션 기록이 있으면 `ALL`로 조회한다. 세션 주문에 대한 매칭은 거래일과 응답에 포함된 주문 거래소도 검사한다. 부분체결 delta 처리와 실제 LOT 반영은 기존 경로를 유지한다.

정상 응답으로 명확하게 거절된 주문은 예약을 해제한다. 해당 세션의 거절 차단 캐시는 프로세스 재시작 시 초기화된다. 불확실한 주문 예약은 DB에 남으므로 재시작으로 해제되지 않는다.

## G. 기존 전략 불변 검증

BUY spacing, VWAP/median/anchor, LOT 개수·금액·상한, profit target, decay, deep loss, reentry, cooldown, risk, 수수료·세금의 계산 코드를 변경하지 않았다. 주문 가격과 수량을 확장 시간에 맞춰 보정하거나 시장가로 바꾸지 않았다.

테스트는 기준 커밋의 실제 `main.py`를 별도 모듈로 읽어 현재 평가기와 동일한 상태·시각·가격으로 실행한다. BUY/SELL 각각에 대해 OFF 및 ON의 정규장 결과에서 주문 가격·수량·판단·LOT·position 상태가 일치함을 확인했다. 핵심 전략 파일 및 운영 config도 기준 커밋과 정규화된 바이트가 같은지 검사했다.

OFF 기본 설정은 기존 config 직렬화/hash에도 확장 기본값을 추가하지 않는다. 다만 이전에 확장 주문이 발생한 DB라면 OFF 전환 후에도 그 주문 대사에 필요한 전체 거래소 조회와 메타데이터 복원은 유지한다.

ON에서는 휴장·시세 유효성·거래소 적격 검사 때문에 기존이라면 진행했을 상황이 차단될 수 있다. 따라서 “ON에서 모든 상황의 주문 결과가 완전히 같다”는 의미는 아니다. 같은 유효한 입력에 대한 전략 계산이 같다는 의미다. 실제로 거래시간을 늘리면 체결·잔고 경로와 이후 전략 상태는 달라질 수 있다.

shadow는 deepcopy한 전략/LOT/position/risk 객체와 읽기 전용 원장으로 같은 판단을 수행한다. 실제 주문이나 모의 체결을 만들지 않으며 target/reentry 상태 변경을 운영 객체에 남기지 않는다. 기존 계좌 대사와 정규장 운용은 별도 유지된다.

- 통신 실패 POST 재전송 방지, 명확한 거절의 예약 해제, 취소 여부 불명의 예약 유지.
- 같은 주문번호라도 다른 날짜/거래소 체결 제외.
- 접수된 주문번호가 기존 원장과 충돌해도 기존 행을 덮어쓰지 않고 예약과 응답 주문번호를 보존.
- shadow 평가가 실제 주문/LOT/decision 원장을 바꾸지 않음.
- 기준 커밋과 BUY/SELL 정규장 판단·가격·수량·상태 비교.
- 기존 LOT 수수료 포함 실현손익을 세션 통계에 그대로 연결. 부가 통계 오류가 LOT 저장을 막지 않음.

## I. 남은 위험 및 실운영 판단

1. **애프터 가격·상태 응답 미확인.** NXT PRE는 실제 조회했지만 NXT/KRX AFTER의 `J/NX` 분봉·현재가와 REST 시장상태의 조합은 실제 세션에서 아직 확인하지 못했다. 미확인 상태는 차단한다.
2. **잔고 평가/현금 입력.** 기존 잔고조회 `AFHR_FLPR_YN=N`과 주문가능현금 계산을 유지했다. 장후 위험 판단에 정규장 평가가격이 남을 수 있고, 애프터에서 기존 주문가능금액 조회가 어떻게 동작하는지 확인이 필요하다. 임의로 X/Y로 바꾸면 risk 입력과 기존 동작이 달라져 이번 작업에서는 변경하지 않았다.
3. **실제 주문 생애주기 미검증.** 원거래소 취소·부분체결 delta·취소 접수 직후의 최종 체결 반영 지연은 모의 응답 테스트만 했다. 실제 API의 일시적 불일치가 발생하면 예약이 남고 종목이 멈출 수 있다. 자동으로 재주문하는 대신 대사 필요 상태를 유지한다.
4. **기존 주문번호 키 한계.** 기존 orders 기본키는 주문번호 하나다. 세션 주문 접수 후 기존 행과 주문번호가 충돌하면 원자적 이름 변경이 실패하고 예약이 남는다. 응답받은 실제 주문번호를 예약 메시지와 오류 로그에 남기고 기존 기록은 덮어 지우지 않는다. 수동 대사가 필요하다. 날짜+거래소 복합키 전환은 운영 DB 마이그레이션을 수반하므로 이 작업에 포함하지 않았다.
5. **체결시각·거래소 정확도.** 일별 체결조회는 주문별 누적 응답이며 실제 체결시각/실행 거래소가 항상 오지 않는다. 주문시각을 체결시각이라고 부르지 않는다. 정확한 체결 세션 손익이 필요하면 실시간 체결통보 또는 정확한 체결시각이 있는 원천이 추가로 필요하다.
6. **처리 시간과 유동성.** 확장 시세 한 번에 여러 GET이 필요하고 원래 표본 추출 횟수를 유지하므로 종목 전체 한 바퀴가 느려질 수 있다. API throttle은 유지했다. 지정가가 체결되지 않거나 오래된 시세 조건으로 계속 건너뛸 수 있다.
7. **새 시간대 자체의 투자 위험.** 같은 전략이라도 더 이른 매수·장후 매도로 자금 사용과 다음 날 보유 상태가 달라진다. 코드 불변 검증은 수익/위험이 같다는 보장이 아니다. 추가 시간의 성과를 아직 측정하지 않았다.

현재 결론: **위험이 현저히 낮다고 단정할 근거가 부족하므로 이번에는 실운영 활성화를 보류했다.** 기존 실매매는 그대로 계속된다. 이는 사용자의 조건부 요청을 평가한 결과이며, 이전 요청의 “실주문 금지”를 기계적으로 적용한 것이 아니다.

다음 실제 검증은 거래소별 애프터 공개 시세와 잔고/주문가능금액 조회 확인, 이어 정상 전략에서 발생하는 주문의 접수→체결/부분체결→취소→DB 수량 일치 확인이다. 일부러 체결되는 시험 주문을 새로 만들거나 수량을 임의로 낮추는 별도 전략은 추가하지 않았다.

### 준비된 활성화 방법

아래는 기능 사용 방법이며 **현재 운영 파일에는 적용하지 않았다**. 기존 `config/lot_auto_trader.json` 최상위에 이 항목만 추가하면 된다. 전체 파일을 예시 파일로 덮어쓰면 안 된다.

```json
"extended_hours": {
  "enabled": true,
  "mode": "live",
  "max_quote_age_seconds": 90,
  "calendar_overrides": {}
}
```

`mode="shadow"`는 확장 시간 판단만 기록하며 정규장 주문은 기존 `order.live_trading`을 따른다. `mode="live"`는 기존 live 설정과 함께 실제 전략 주문을 허용한다. 모의 클라이언트는 확장 시세 검증을 통과하지 않도록 했다.

새 Python 소스는 실행 중 프로세스에 자동 반영되지 않는다. **이번 코드를 처음 배포할 때는 기존 실행 방식으로 봇 프로세스를 한 번 교체해야 한다.** 구버전 프로세스의 config reload만으로 새 클래스가 로드되지 않는다. 이미 새 코드로 시작한 뒤에는 기존 안전한 config reload 절차를 사용할 수 있다. 기존 프로세스와 새 봇을 동시에 실행하지 않는다.

원복은 `enabled=false`. 이미 접수된 주문/부분체결은 삭제하지 않고 계속 대사한다. 불명확한 `INTENT`를 임의 삭제해서 다시 주문하지 않는다. `session_trade_blocked`, `session_order_rejected`, `order_submission_unknown`, `session_order_reconciliation_required`, `session_lot_audit_failed` 로그를 확인한다.

### 성과 기록

세션 주문이 처음 기록될 때 `order_session_metadata`, `fill_session_metadata`, `fill_lot_attribution` 테이블을 추가한다. 기존 orders/fills/LOT 스키마나 과거 데이터는 변환하지 않는다. 이번 작업에서는 운영 DB에 테이블을 만들지 않았다.

```powershell
.\.venv\Scripts\python.exe scripts\report_session_activity.py --db data\lot_auto_trader_real_test.sqlite3
```

집계는 매수/매도금액, 기록된 체결 건수, 기존 LOT 계산의 비용 포함 실현손익, 매수 주문 세션→매도 주문 세션을 출력한다. 기존 LOT 매수 세션은 UNKNOWN일 수 있다. 체결시각이 주문시각뿐인 경우 실제 체결 세션도 UNKNOWN이다. 실제 체결 거래소는 확인되지 않으면 빈 값으로 둔다. 미연결 SELL 건수와 미추적 과거 체결 건수를 함께 출력하며, 미연결 손익을 0원 수익으로 해석하면 안 된다. 누적 체결 delta 건수는 거래소 체결 tick 수와 같지 않다.

## J. diff 요약과 자체 리뷰

핵심 변화는 **세션/가격 어댑터 → 기존 전략 평가 → 기존 가격·수량 주문에 route 부착 → 단일 주문 예약/대사**다. 전략 수식/파라미터와 운영 파일은 그대로다. 실제 diff는 이 브랜치 working tree에 있으며, 새 파일은 위 B에 모두 나열했다. `git diff`만 보면 미추적 새 파일은 나오지 않는 점에 유의한다.

| 자체 리뷰 질문 | 결론 |
|---|---|
| 전략 계산식 변경? | NO. 핵심 파일 동일 및 BUY/SELL 비교 테스트 |
| 정규장 동작 변경? | OFF 기존 동작. ON에는 유효성 차단/예약/대사 보호 추가, 전략 계산 동일 |
| 한 신호의 KRX/NXT 중복 주문? | 단일 route 및 원장 예약으로 차단. 결과 불명 시 다른 거래소 재전송 안 함 |
| NXT 비대상 주문? | 적격 Y/정지 N 확인 없으면 차단 |
| 세션 전환 시 pending 유실? | DB에서 원래 route 복원, 확인 불가 시 예약 유지 |
| reserved cash 이중 차감? | 접수 전 예약을 응답 주문번호로 원자적 변경, 원장 한 행 유지 |
| 같은 LOT 중복 SELL? | LOT별 미결 검사와 트랜잭션으로 차단 |
| 종료 후 신규주문? | 평가·표본·전송 직전 시각 확인. 확인과 네트워크 전송 사이 아주 짧은 경합은 거래소의 접수 판단에 따름 |
| 휴장일 주문? | ON 휴장 조회·실시간 상태 확인, 실패 시 차단. OFF 기존 정책 유지 |
| OFF 기준 커밋 동작? | 기존 테스트/전략 비교 통과. 이전 확장 주문의 사후 대사는 예외적으로 유지 |
